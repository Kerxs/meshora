# 六大能力

::: warning 当前状态
P2P 和 Relay 在 M1 里有了第一版实现（Linux 上验证过，NAT 是模拟的，还没在真实网络里测过），
其余四项**尚未实现**。本页描述的是设计意图与已知的技术难点。
:::

能力是 Node 对网络的声明：我能提供什么。一个 Node 可以同时提供多项，也可以只提供一项。

| 能力 | 一句话 | 主要难点 |
| --- | --- | --- |
| [P2P](#p2p) | 设备之间直接连接 | NAT 穿透成功率 |
| [Relay](#relay) | 直连失败时中继转发 | 中继选择与带宽成本 |
| [Gateway](#gateway) | 提供网络出口 | 路由与 NAT 配置 |
| [Virtual LAN](#virtual-lan) | 创建虚拟局域网 | 广播帧转发 |
| [Game Node](#game-node) | 为多人游戏提供连接 | 老游戏的局域网发现 |
| [Application Routing](#application-routing) | 按应用/域名/IP/端口选路 | Windows 上的进程级分流 |

## P2P

**技术实质**：NAT 打洞成功后，把对端的 endpoint 写进 WireGuard 的 peer 配置，流量直连。

这是默认且首选的路径。延迟最低，不消耗任何第三方带宽，也不产生流量成本。

同一局域网内的两个节点会走局域网直连，不绕公网 —— 这个判断在[节点发现](/guide/connection-flow#_1-节点发现)阶段就完成了。

## Relay

**技术实质**：中继节点转发**已被 WireGuard 加密的报文**。它看不到明文，也改不了内容。

中继的作用是**保证可用性**，不是提供性能。设计上采取"中继先行"策略：
连接立刻经中继建立，打洞在后台继续，成功后无缝切到直连。

一个节点要当中继，前提是有稳定的公网可达地址。它需要考虑的问题是带宽成本 ——
中继转发的流量是实打实要付钱的，所以 ACL 里要能限制谁可以用。

## Gateway

**技术实质**：出口节点对应的 peer 配置里 `AllowedIPs` 设为 `0.0.0.0/0`（和 `::/0`），
其余节点把默认路由指向它；网关侧开启 IP 转发并对出站流量做 NAT。

典型用途是出差时把流量绕回家里的网络，访问只对家庭宽带开放的服务。

需要注意的坑：

- **DNS 必须跟着走**，否则会在本地解析出错误的结果，还会泄漏查询记录
- **别把网关自己的流量绕进隧道**，否则形成路由环路
- 网关节点需要管理员权限来改路由表和开启转发

## Virtual LAN

**技术实质**：每个节点分配一个 overlay IP，经 TUN 设备路由。地址段候选是
CGNAT 段 `100.64.0.0/10`（和 Tailscale 同样的思路，几乎不会和家用网段撞车）或 IPv6 ULA。

比起简单的点对点隧道，虚拟局域网多出来的关键一步是**广播与组播转发**。

绝大多数"局域网发现"依赖的都是广播或组播：网络邻居、AirPlay、打印机发现、
各类游戏的房间列表。如果 overlay 只转发单播，这些功能全部失效 ——
设备互相 ping 得通，却在彼此的列表里看不见对方。这时候"虚拟局域网"这个说法就名不副实了。

代价是广播会在整张网里扩散，节点一多就是负担。所以需要**广播域的概念**：
允许把网络切成若干段，广播只在段内扩散。

## Game Node

**技术实质**：一个为低延迟优化的档位，外加对局域网游戏发现机制的针对性支持。

这项能力的难点不在带宽，在于**很多游戏的联机发现依赖 UDP 广播**。
一款 2005 年的游戏会往 `255.255.255.255` 的某个端口发探测包，然后监听回应来列出可加入的房间。
要让它在虚拟局域网里正常工作，就得把这些广播帧真正转发过去（见上一节）。

除此之外，低延迟档位意味着：

- 选路时**抖动的权重高于绝对延迟** —— 稳定的 60ms 比在 20~90ms 之间跳变的体验好得多
- 倾向直连，容忍更激进的打洞重试
- 尽量避免为了省带宽而做的缓冲和聚合

## Application Routing

**技术实质**：按应用、域名、IP、端口决定流量走哪条路径。这是六项里工程量最大的一项。

四种匹配维度的难度差得很远：

| 维度 | Windows 上怎么做 | 难度 |
| --- | --- | --- |
| IP / 端口 | 路由表 + 防火墙规则 | 低 |
| 域名 | 拦截 DNS，把解析结果映射到策略 | 中 |
| 应用（进程） | **WFP**（Windows Filtering Platform），按 PID 关联流量 | 高 |

按进程分流必须走 WFP：在过滤层拿到每个连接的发起进程，再决定放行到哪条路径。
这需要一个 WFP callout 驱动或者用户态的 ALE 层过滤，实现和调试成本都不低。

按域名分流还有个绕不开的麻烦：**DoH/DoT 把 DNS 加密了**。
应用自带的加密 DNS 会绕过系统解析器，导致拦截失效。要么劫持并代答，要么接受这类流量落到默认策略。

把代价写在这里，是为了避免"配个规则就行"的错觉。这一项大概率会排在路线图较后的位置 ——
见[路线图](/guide/roadmap)。
